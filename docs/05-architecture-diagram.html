Interaction loop — sync, cheap

Everything that isn't the agent

No LLM call anywhere in this path — this is what keeps event ingestion cheap under bursty tracking traffic.

Event ingestion

Client batches model_view / search / model_compare / dwell and flushes via sendBeacon or timer — bulk insert, not one call per click.

→ SQL: events

Admin dual-write

Create/edit/delete a model writes SQL and upserts Chroma in the same request; a failed vector write leaves vector_synced=false, never a silent gap.

→ SQL: models → Chroma: upsert

Catalog browse / search

Filter by modality, provider, or use-case — reads straight from SQL, no retrieval involved.

← SQL: models

Trigger evaluator — still no LLM

Runs inline right after the event batch insert, one cheap SQL check: events_since_last ≥ 5, or time_elapsed > 10min with new activity, gated by a 2-minute cooldown. If it fires, a background task is scheduled — the HTTP response to the browser is never blocked on the agent run.

Recommendation loop — async, LLM-bearing

Agent pipeline (LangGraph), 5 named nodes

Runs as a background task. Exactly one node ever calls an LLM — everything before and after it is deterministic code.

Bonus / optional

Scheduler — APScheduler, in-process

Sweeps active users on a cron and reuses the same 5-node pipeline to produce a proactive digest.

→ Email / Telegram

LangSmith tracing

Taps the pipeline for an inspectable trace per run — off the request path either way.

External service

Mesh API

OpenAI-compatible base URL. Every LLM call in the system — there is exactly one, in generate_narrative — routes through here. No direct OpenAI/Anthropic/Gemini client is ever configured outside this.

↩ Back to the browser: Dashboard reads the latest recommendations row (GET /recommendations/me). Your Activity reads the raw event log plus that same row's behavior_summary / activity_hash / trigger_reason (GET /activity/me) — a read-only second view over data the pipeline above already had to persist, not a new write path.
